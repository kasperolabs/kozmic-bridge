# Indexer spec: Kozmic, Ethereum to Kaspa

For an indexer, explorer or wallet that should recognize Kozmic activity on Kaspa mainnet, decode it,
and link each mint to the Ethereum deposit behind it. Updated 2026-10-13.

Read from a Kaspa node's RPC, not from explorer pages: explorers only partly decode v1 transactions
with covenants. Per transaction the indexer needs each input's signature script and UTXO entry
(script public key, covenant id), and each output's script public key, value and covenant binding.

---

## 1. What to recognize

| class | what it is | how to recognize it |
|---|---|---|
| `bridge.genesis` | creation of a bridge covenant instance | an output bound to a covenant id in the configured list, whose authorizing input does **not** carry that id (KIP-20 genesis) |
| `bridge.init` | binding the instance to its KCC-20 token | the instance's first spend: 2 outputs, output 1 is a fresh covenant genesis (the token) |
| `bridge.advance` | one state transition: a light-client step, and mints if the journal carries new deposits | an input whose UTXO carries a configured bridge covenant id, after init |
| `token.transfer` | a wallet-side move of minted tokens | an input whose UTXO carries the token's covenant id, with no bridge input in the transaction |

Identify instances by **covenant id**, never by address: the P2SH address changes on every advance
(the state is inside the redeem script), the covenant id is fixed for the life of the instance.

## 2. Decoding a `bridge.advance`

The signature script is a sequence of data pushes: the entry arguments and a dispatch selector
generated by Silverscript, then `push(redeem_script)` as the **last** push. Do not depend on argument
positions (a Silverscript ABI detail). Instead:

1. Parse the signature script into pushes (OpData1..75, OpPushData1/2/4, small ints).
2. `redeem = last push`. Optionally check `blake2b(redeem)` against the spent UTXO's P2SH hash.
3. `proof = the push of exactly 128 bytes` (compressed Groth16 proof).
4. `journal = the push whose length is 230 + 49n` (section 3) **and** whose first 32 bytes equal the
   instance's chain commitment. Exactly one push matches.
5. `journal_hash = sha256(journal)`, the value the proof was verified against.

Outputs of an advance, in order:
- **output 0:** the bridge successor (same covenant id). Its value is the bridge's new KAS balance.
- **heartbeat** (no new deposits): nothing else bound to the token; the transaction has no token input.
- **mint:** output 1 is the continuing minter branch (token covenant id, state
  `{bridge covenant id, 0x02, 0, true}`), then outputs 2, 3, ... are the recipient token UTXOs, one per
  newly minted deposit, in nonce order. The transaction has exactly one token input, the previous
  minter branch.

The bridge state after an advance (header, committee, cursor) is also embedded in the successor's
redeem script (bytes 1..108: `header byte[32] | committee byte[32] | cursor int | token byte[32]`),
but read header and committee from the journal and the cursor from the last minted nonce.

## 3. The journal (frozen 2026-10-12): `len = 230 + 49n`, big-endian

```
0    32  chain_commitment
32   32  prev_header       finalized beacon header root the covenant trusted
64   32  prev_committee    sync committee hash the covenant trusted
96   32  new_header        new finalized beacon header root
128  32  new_committee
160  8   new_slot          beacon slot of new_header
168  32  exec_state_root
200  8   exec_block_number
208  20  vault             Vault.sol address, all zero when n = 0
228  2   deposit_count n
230  49n deposits, each:
           +0   8   nonce      strictly increasing within a journal
           +8   8   amount     token base units (6 decimals for KBT)
           +16  33  kaspa_spk  version byte | 32-byte payload
```

`kaspa_spk` to address: version 0 = P2PK Schnorr (`kaspa:q…`), version 8 = P2SH (`kaspa:p…`); standard
Kaspa bech32 with prefix `kaspa` over version byte + payload. Other versions cannot appear (the
program refuses them).

The retired test instance used an older layout, `len = 210 + 84k` (a 2-byte slot count at 208, then
raw storage slots); all its advances have k = 0. The two families never collide in length.

## 4. Classifying an advance

| sub-class | condition |
|---|---|
| `heartbeat` | no deposit in the journal has a nonce above the previous cursor: header and committee advance, nothing is minted |
| `mint` | one or more deposits above the previous cursor: each produced one recipient token output |
| `rotation` (flag, combinable) | `new_committee != prev_committee`: the step crossed a sync-committee period |

**A heartbeat still carries a deposit.** The covenant requires the journal's vault field to equal the
vault on every advance, and a journal with no deposits has an all-zero vault field, so heartbeats
re-prove the deposit at the cursor. Do not classify by `deposit_count`; classify by whether any
nonce exceeds the cursor before the advance.

Per minted deposit record: nonce, amount, recipient address, token output index, mint txid. A nonce
is minted at most once per instance (the cursor enforces it); seeing the same nonce minted twice is
an indexer bug, not a state to display.

## 5. Recipient token UTXOs (the KCC-20)

A token UTXO is a P2SH covenant output bound to the token's covenant id. Its redeem script is
`template_prefix (1 byte) || state || template_suffix (2615 bytes)`; the template hash above
identifies the token class, the covenant id identifies this token. State, each field with its push
prefix: `ownerIdentifier byte[32] | identifierType byte | amount int (8-byte LE script number) |
isMinter bool`.

| identifierType | owner | spent by |
|---|---|---|
| `0x00` | x-only public key (= a `kaspa:q…` address payload) | a Schnorr signature with that key |
| `0x01` | script hash (= a `kaspa:p…` address payload) | including an input whose script is that P2SH |
| `0x02` | covenant id | including an input of that covenant (only the minter branch, owned by the bridge) |

To show a balance: sum `amount` over unspent UTXOs bound to the token's covenant id whose owner
matches the address payload. Transfers conserve `amount`; only the minter branch changes supply, and
only with a bridge input present.

## 6. Linking to Ethereum

Join key: **(vault address, nonce)**. The journal does not contain the Ethereum transaction hash.

Ethereum side (any execution RPC, `eth_getLogs` on the vault, from its deploy block 26,178,399 =
`0x18f735f`, to `"finalized"`, in pages of at most a few thousand blocks on public endpoints):

```
event Deposited(uint64 indexed nonce, address indexed from, uint64 amount, bytes kaspaSpk)
topic0 = 0x9c0e9486faca41639fcc24cb5c2ada10effee01bebc1fc7665d71e8b9a944375
topic1 = nonce (uint64, left-padded to 32 bytes)
topic2 = depositor address
data   = abi.encode(uint64 amount, bytes kaspaSpk)
```

A keyless endpoint is enough for the vault's volume: `https://ethereum-rpc.publicnode.com`.

### Deposit status

```
deposited   Deposited event seen (unfinalized logs can still disappear in a reorg)
finalized   deposit block <= exec_block_number of the latest finalized beacon header
minted      a bridge.advance journal contains (vault, nonce) with nonce above the previous cursor,
            and the same transaction holds the recipient token output
```

Proving and minting happen in one Kaspa transaction. Expected deposited-to-minted time: Ethereum
finality (14 to 30 minutes observed) plus about 5 minutes of proving and submitting while a prover is
running (18.5 minutes measured for deposit #3). A deposit never expires; if no prover runs, it waits.

## 7. What to show a user for one deposit

Ethereum deposit tx and block; the beacon slot that finalized it; the Kaspa mint tx with covenant id,
journal hash and image id; the recipient address and amount; the token UTXO. The image id is the one
check a skeptic cannot do on an explorer: link the source and the Docker build that reproduces
`4756d736…` (top-level README).
